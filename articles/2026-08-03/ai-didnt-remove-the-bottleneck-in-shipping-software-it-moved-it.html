AI Didn't Remove the Bottleneck in Shipping Software. It Moved It.

3 August 2026 · synthesised from 3 sources

When an agent can write code faster than any person can read it, the limit on how much you can safely automate stops being model quality and starts being how cheaply you can check what came out, and that number is set by your architecture, not your AI.

The mouth got wider; the neck didn't

Claude Code and Codex can turn out a working pull request faster than any person can read one, and that has quietly relocated the real constraint on vibecoded software. It used to be how fast the AI could generate code. Writing on 20 July, Google's Addy Osmani framed what replaced it: "the fundamental constraint in a software factory isn't how much code we can churn out: it's how quickly we can verify it." He borrows the factory metaphor deliberately. A "loop" is one agent doing a single job on repeat: gather context, take an action, check the result, go again. A "harness" is the sandbox, tools and memory around that loop. A "factory" is many harnessed loops running at once, fed by a queue and drained through a review gate. Manufacturing has run this exact trade-off since FANUC's fully automated "lights-out" plants in 2001 and Xiaomi's 2024 facility, where the lights stay off because only machines are working. Osmani calls the automation-with-no-human-review version a dark factory, and the version where a person still reads the output before it ships a light factory.

The quiet, late reckoning

Osmani cites Dex Horthy, founder of HumanLayer, who ran a fully autonomous dark factory for four months with no human code review at all. When something eventually broke, it wasn't dramatic. As Horthy put it, "it required painstaking manual debugging to pinpoint." That's the mechanism Osmani names comprehension debt: the widening gap between how much code exists and how much any human still understands. A dark factory doesn't pay that debt down. It borrows against it as fast as it can generate. "The ultimate reckoning, when it comes, will not be a dramatic 'it all goes sideways' moment. It will be quiet and late." Generation is a wide funnel mouth; verification is the narrow neck it all has to pass through. Speeding up the mouth just deepens the pile at the neck; it doesn't widen it.

Architecture is what sets your verification bill

This is where advice you've probably already half-absorbed gets a price tag attached. Engineering blogger CodeOpinion lists the coupling patterns that quietly make a codebase expensive to check: entity models built around plain CRUD, where an order object is just an ID, a status and a total, and "the business logic... often stays in the end users' heads" instead of the code; a shared database table used as the integration point between parts of a system, so nobody can say who owns a column or what breaks when it changes; and an abstraction wrapped around a single implementation: as CodeOpinion puts it, "you hide coupling behind interfaces rather than removing it." None of that is new advice. What's new is why it now matters more: every hidden coupling widens the blast radius of a change, and blast radius is exactly what an agent's check has to cover before you can trust its diff. An operation named CancelOrder instead of a generic UpdateOrder isn't a style preference any more: it's the difference between a check that can verify one intent and a check that has to reason about everything an "update" might mean.

Where the rule actually bites

YouTuber Chris Raroque's own build shows the boundary. His iMessage-based agent, Boop, already reached hundreds of tools through the integration platform Composio. The features people kept requesting instead were iMessage, Apple Notes and Apple Reminders, services with no public API at all, which Raroque says is "the reason... even ChatGPT and Claude don't have access to these things." He got there anyway, using Claude Code to reverse-engineer the access, and found it "a lot easier than I expected." That's precisely the move Osmani's rule warns about: "you can only hand a loop as much autonomy as you can cheaply and reliably verify, and not one inch more." An undocumented, unofficial integration has no contract to test against — the check on it can't be cheap or automatic, only manual and ad hoc, one feature at a time. Horthy's own "12-Factor Agents" guidance backs this with a number: agent loops hold together for roughly three to ten steps and reliably start losing the thread past twenty. A dozen small, checkable tasks beat one long unsupervised run, even when the long run would technically finish faster.

Where to put the switch

Osmani's closing image is a factory floor where you can't find the light switch. The fix isn't reviewing every line an agent writes; it's deciding, loop by loop, which ones have earned darkness. Pick one part of whatever you're building right now that currently ships without you reading the diff: a background job, a webhook handler, a data migration. Ask if the check on it is cheap, runs often and is hard to fake out. If it isn't, that's the light to turn back on first: not by babysitting the agent, but by adding the type, the test seam or the schema contract that lets a machine catch the mistake before it reaches you.
