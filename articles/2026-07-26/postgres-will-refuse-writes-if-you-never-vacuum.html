Postgres Will Eventually Refuse Every Write If You Never Vacuum

26 July 2026 · synthesised from 3 sources

Postgres never deletes a row when you tell it to: it marks the old version dead and leaves it on disk, which is why a mass delete doesn't shrink your database and, left unmanaged long enough, why the database can stop accepting writes altogether.

The DELETE that doesn't delete

Delete a hundred thousand rows from a Supabase table and check the project's disk usage a minute later: it hasn't moved. That's not a dashboard lag. Postgres never actually erases a row when a DELETE commits. It flips a hidden field called t_xmax to record which transaction killed the row, and leaves the bytes exactly where they were. An UPDATE does the same thing twice over: the old row version is marked dead and a new version is written elsewhere on the page. This is MVCC, multi-version concurrency control, the reason one connection can read a consistent snapshot of a table while another is mid-write to it without either one blocking the other. The cost of that trick is that every row you think you deleted is still sitting on disk as a "dead tuple," and the page's internal free-space bookkeeping doesn't update either. Insert a new row next, and Postgres skips straight past the page you just freed and extends the file with a fresh one, because nothing has told it the space exists.

Vacuum's actual job

Reclaiming that space is what VACUUM does, and it runs in phases rather than one sweep. First it scans the table and prunes dead tuples from each page, defragmenting what's left; a worked example from the Postgres-focused blog BoringSQL shows a single 8 KB page recovering 2,176 bytes by pruning just 16 dead rows. If the table has indexes, a second, more expensive phase reads every index page hunting for entries that still point at those dead rows. Only once those are gone can a third phase mark the row's slot as fully reusable; in the same example, the table's index shrank from 50 entries to 34. None of this happens because you asked. Autovacuum is a background worker enabled by default on every Supabase project, watching each table's dead-row count and triggering a VACUUM once enough of it has piled up.

Why the file itself doesn't shrink

Here's the part that catches people out: even after autovacuum runs, the table's file on disk usually doesn't get smaller. A plain VACUUM only returns space to the operating system when it can truncate whole pages off the end of the file, which means every row on those trailing pages has to be dead. BoringSQL's test makes the difference concrete: deleting a contiguous block of rows from the end of an 18-page table let VACUUM truncate it down to a single page, but deleting every second row across those same 18 pages left every page holding at least one surviving row, so the file stayed at 18 pages. The freed space sits stranded inside the file, available for Postgres to reuse on the next insert, but invisible to a disk-usage graph. "I deleted a huge chunk of data and the database is the same size" is normal, not broken.

The tempting fix, and why it's a last resort

VACUUM FULL looks like the answer: it rewrites the table from scratch and hands the freed pages back to the OS, 18 pages down to 9 in that same test. The catch is the lock. Standard VACUUM takes a ShareUpdateExclusiveLock, so reads and writes carry on around it; VACUUM FULL takes an AccessExclusiveLock, blocking every read and write on that table until it finishes. Supabase's own guidance is blunt about it: run a plain vacuum; to reclaim reusable space without locking anything, and reach for vacuum full only on a specific table, off-peak, when the file genuinely needs to shrink. The CLI's inspect db bloat command shows you whether that's even true before you touch a production lock.

What happens if nobody vacuums

This isn't just housekeeping. Postgres tracks transaction age with a 32-bit counter, and MVCC visibility works by comparing one transaction's ID against another's. Left unfrozen indefinitely, that counter would wrap around to zero, and old committed rows would suddenly look like they came from the future and vanish from view. VACUUM prevents this by "freezing" old rows against a sentinel value that always sorts as older than anything real, and Postgres forces the issue if that never happens: the documentation requires vacuuming every table at least once every two billion transactions, warns once a database is 40 million transactions from that limit, and at 3 million remaining stops accepting any transaction that would assign a new write ID. Read-only, full stop, until an emergency vacuum runs. It's a rare failure, usually caused by a forgotten long-running transaction or a stuck replication slot holding old rows visible, but it's the one case where "autovacuum handles it" isn't quite true, since autovacuum can itself be blocked by exactly that kind of stuck transaction.

Check this on your own project

Run select relname, age(relfrozenxid) from pg_class where relkind = 'r' order by 2 desc limit 5; against your Supabase database this week. Anything climbing well past a few hundred million with no plateau is worth tracing back to whatever's holding a transaction open. A debugging session left connected in a SQL client is a common culprit. It costs one query to check, and a locked table to find out the hard way.
